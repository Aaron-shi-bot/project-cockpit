# Feature Specification: 项目驾驶舱 Sites公开部署

**Feature Branch**: `002-sites-deployment`（功能标识；当前工程无Git分支操作）

**Created**: 2026-10-23

**Status**: 云适配已实现，适配测试及本地Worker后端已取得证据；浏览器与生产验收尚在推进，不是上线完成记录

**Input**: 用户最新U-14允许通过Codex Sites公开部署；沿用现有内置账号、邀请、权限和界面，不携带本机账号及演示数据。

依据：[PRD REQ-020及U-14](../../../需求/PRD.md)、[001业务规格](../001-team-cockpit/spec.md)。001的REQ-001—013、现行接口口径和视觉基准继续适用；REQ-014—019仍为候选。本切片只增加公开部署、受保护的首位所有者建立及云端持久化条件，不重做平台设计。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 安全打开公开驾驶舱 (Priority: P1)

用户打开公开网址，只有持有专用初始化凭据的人能在全新工作区建立首位所有者。其他访客看到登录或邀请入口，无法抢先取得所有权。建立后继续使用平台账号登录。

**Why this priority**: 网址公开后，所有权不能由先访问的陌生人取得。

**Independent Test**: 在隔离的空工作区依次尝试无凭据、错误凭据和正确凭据建立账号，并同时提交两次有效建立请求；确认最终只产生一个工作区和一名有效所有者，随后可正常登录。

**Acceptance Scenarios**:

1. **Given** 全新工作区且未提供有效初始化凭据，**When** 任意访客打开页面或尝试建立所有者，**Then** 不能创建账号、取得团队数据或改变初始化状态，页面给出明确提示。
2. **Given** 有效的一次性初始化凭据，**When** 用户建立首位所有者，**Then** 创建一个空工作区并进入平台；不自动导入项目、成员、文件或演示数据。
3. **Given** 两位访客同时使用有效凭据建立首位所有者，**When** 请求完成，**Then** 至多一人成功，另一人明确得知已建立，不能出现两个所有者或部分账号。
4. **Given** 工作区已建立，**When** 再次使用原初始化凭据，**Then** 不能重置所有者、密码或工作区。
5. **Given** 用户完成初始化、登录和退出，**When** 检查地址、页面、历史与可下载产物，**Then** 初始化秘密不出现在URL查询、页面持久存储、静态代码、日志或业务导出中；退出后原会话不能继续访问。

---

### User Story 2 - 团队从外网按既有权限协作 (Priority: P1)

所有者通过现有邀请方式建立团队，成员从另一台设备加入、查看有权项目并更新工作。公开网址只改变访问地点，不扩大任何人的业务权限。

**Why this priority**: 上线的价值是团队可用，权限退化会泄露项目与文件。

**Independent Test**: 在隔离工作区建立所有者、协作成员和只读成员，完成邀请、任务更新、多源授权与完全撤权；用另一浏览器及直接请求确认后续访问立即按新权限处理。

**Acceptance Scenarios**:

1. **Given** 有效管理员生成了指定项目和角色的邀请，**When** 受邀人打开链接并加入，**Then** 只获得所列身份与项目范围；重复、过期、撤销及邀请人失权的链接均不能再次生效。
2. **Given** 成员同时有直接与团队授权，**When** 依次撤销不同来源，**Then** 有效角色按现有规则变化；全部撤销后的下一次读取、写入和历史文件下载均拒绝。
3. **Given** 成员已停用，或工作区管理员未获某项目授权，**When** 使用旧页面、会话或下载地址访问，**Then** 不返回未授权的名称、统计、正文、版本信息或字节。
4. **Given** 成员按既有角色更新任务、风险、评论或项目，**When** 保存成功或因冲突、再次认证失败，**Then** 保持001规定的业务结果与提示；失败不静默丢掉草稿或扩大授权。

### User Story 3 - 工作和文件在云端长期保留 (Priority: P1)

成员保存项目与两个文件版本后，即使服务重新启动、换设备或两人同时修改，仍能看到已确认的最新工作和完整历史；失败请求不能留下半份业务结果。

**Why this priority**: 可打开网页不足以证明是可用的多人项目系统，必须避免重启丢失和并发覆盖。

**Independent Test**: 上传两个不同内容的文件版本并记录摘要，执行竞争更新，再重新启动本地云运行环境及重新部署相同线上代码；重新登录后核对项目、授权、版本摘要和冲突结果。

**Acceptance Scenarios**:

1. **Given** 有权成员上传了两个版本，**When** 下载历史与当前版本、恢复旧版，**Then** 原两版内容均保持不变；恢复形成新版本，且每次下载重新鉴权。
2. **Given** 两人读取相同版本，**When** 同时提交不同修改，**Then** 最多一个成功，另一人得到明确冲突；任务与关联阻塞、审计和授权不出现部分更新。
3. **Given** 保存已成功并记下记录与文件摘要，**When** 服务冷启动或相同代码重新发布，**Then** 重新登录后数据、权限与文件字节完整，未再次导入本机库或演示数据。
4. **Given** 文件上传或数据保存中途失败，**When** 用户重试，**Then** 不产生重复版本、坏下载记录或未授权的文件；失败残留不公开可访问。

### Edge Cases

- 初始化秘密未配置、为空或错误：建立入口关闭，不能退回无保护模式。
- 初始化与邀请接受同时重试：不重复建用户，不改变原有唯一所有者规则。
- 撤权后重放旧请求编号或旧下载地址：按当前权限拒绝，不能通过已缓存的响应取回内容。
- 多个运行实例竞争同一业务版本：不得靠单进程锁、内存会话或浏览器数据决定最终状态。
- 文件写入成功而业务提交失败，以及相反次序：用户只能看到完整、可下载的已提交版本；不把孤立字节当作有效资料。
- 已完成/归档、恢复、最后维护者、工作区所有者、时区与日期边界：沿用001，不因部署迁移另设宽松规则。
- 本机演示入口、演示会话与固定账号：不能成为线上自动登录或预置账号。
- 站点构建成功、平台报告部署成功、生产业务验收成功及用户设计确认是四种独立状态。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供用户已授权的公开HTTPS访问入口，并沿用既有页面与导航；匿名访客不能访问团队业务内容。对应REQ-020、REQ-006、008。
- **FR-002**: 系统必须仅允许持有高熵一次性初始化凭据的人在空工作区建立首位所有者；未配置、无效或已消费的凭据不能建立或重置账号。对应REQ-020、011。
- **FR-003**: 首次建立必须不可分割且只成功一次；并发与重试不能出现多所有者、重复工作区或部分账号。对应REQ-020、011、012。
- **FR-004**: 系统必须保持初始化秘密只用于首次建立，不保存在公开地址查询、静态产物、浏览器持久存储、日志或业务导出中。对应REQ-020。
- **FR-005**: 云端必须从独立空工作区开始，不携带本机账号、会话、数据库、上传文件及4174虚构项目；不能开启演示自动登录。对应REQ-020。
- **FR-006**: 内置登录、邀请、工作区及项目角色、多源授权、停用、再次认证和最后所有者/维护者保护必须与001一致，不增加公开注册或邮件发送。对应REQ-011、020。
- **FR-007**: 每次读取、统计、修改、历史查看和文件下载必须验证当前有效身份及权限；撤权后旧会话、地址、请求编号和页面缓存不得继续提供受限内容。对应REQ-001、009—011、020。
- **FR-008**: 云端必须持久保存已确认的业务记录、授权、历史、审计和私有文件，跨设备、冷启动及相同代码重新发布后保持完整。对应REQ-010—012、020。
- **FR-009**: 文件历史不可覆盖；上传两个版本及恢复旧版后，历史字节与版本关系必须可核对，每次下载仍按当前项目权限决定。对应REQ-010、020。
- **FR-010**: 并发更新必须保持既有版本冲突、完整业务提交与重试去重；不能静默覆盖任务、风险、授权或文件关系。对应REQ-012、020。
- **FR-011**: 失败请求必须不给用户显示半份成功结果，文件残留不能公开读取；日志和错误响应不得包含密码、会话、初始化秘密或完整邀请凭据。对应REQ-010—012、020。
- **FR-012**: 交付必须分别记录本地云运行、实际线上业务验证、部署网址及用户设计反馈；未执行项明确保留，不把本机测试或发布成功替代这些结论。对应REQ-020、007、013。

### Key Entities

- **部署环境**：公开访问地址、当前发布版本、独立业务存储与私有文件存储的组合；本机与线上彼此隔离。
- **初始化状态**：是否已建立首位所有者、建立时间与一次性建立资格；不承担日常登录授权。
- **既有业务与安全记录**：成员、项目、任务、里程碑、风险、资料版本、授权、会话、邀请和审计，含义继续由001及现行接口合同定义。
- **提交版本**：保护一次完整业务变更的冲突依据；不能替代每个对象已有的业务版本或当前权限。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在空工作区，无凭据、错误凭据、已消费凭据均无法建立所有者；两次同时有效建立最终恰好一个成功。
- **SC-002**: 使用公开网址完成“初始化或登录→建项目→邀请加入→协作更新→全部撤权”一条完整路径；撤权后的下一次业务请求与历史下载均拒绝。
- **SC-003**: 一个资料保留两版不同内容；恢复旧版产生第三版，原两版摘要不变，撤权者无法下载其中任何一版。
- **SC-004**: 两次竞争同一版本的修改至多一个成功；一次重试不产生第二条业务记录或版本，不出现缺少关联阻塞或审计的半份更新。
- **SC-005**: 本地运行重启与线上相同代码重新发布后，验收样本的记录数量、权限和文件摘要完全相同；不把刷新页面等同冷启动。
- **SC-006**: 本切片全部P0验收用例分别取得本地及适用线上证据；交付清楚区分未测项、上线结果与待用户确认的视觉设计。

## Assumptions

- 当前是一个团队工作区，继续使用001的固定角色和账号邀请；不会因公开站点转成多租户或匿名协作平台。
- 用户U-14已授权创建与发布公开Sites站点；平台可提供站点地址，无需先购域名。站点创建、存储配额及发布是否成功仍以实际工具结果为准。
- 初始化秘密由部署方安全生成并私下交付，源码和文档只记录配置名称及流程，不写入真实值。
- 本轮保留既有视觉，不启动新VI或页面重设计；公开发布并不等于用户逐页设计验收通过。
- 本轮不自动导入旧库，不约定未经测试的并发人数、可用性或容量；定时备份与灾难恢复能力若未实测，交付中明确列为缺口。
