## 本机运行

需要Node.js 24.14或更新版本。Windows运行本目录的启动.ps1，或在本目录执行：

```powershell
npm.cmd ci --registry=https://registry.npmjs.org
npm.cmd run build
npm.cmd start
```

浏览器访问 http://127.0.0.1:4173 。首次自行创建所有者，没有默认密码；默认数据库没有演示项目。所有者可在空页面主动导入6个虚构项目。账号与业务保存在data/cockpit.sqlite，浏览器刷新不丢数据。

邀请由设置页创建链接，管理员通过已确认的私下渠道交给收件人。链接包含一次性凭据，应按账号访问凭据保管；平台不自动发邮件，也未接邮箱所有权验证。邀请索引使用凭据散列；写入请求的幂等响应可能保留首次返回的邀请凭据，因此数据库和备份也须按访问凭据保护。邀请接受时再次检查发起人的授权。

开发调试另开两个终端：npm run dev（5173，代理API），npm start（4173）。日常试用直接使用4173上的构建版。

## 云服务器首次启动

采用一台Linux云主机上的同源服务、SQLite持久卷和Caddy HTTPS。初始版本适合单实例；多人规模与容量尚未作生产压测。首次初始化须在受控网络完成，避免未初始化服务被外部账号抢先设置。

1. 安装Docker与Compose，将本工程复制到服务器，排除node_modules、.npm-cache、data以及任何本地.env。
2. 复制.env.example为.env，填写真实域名。初始化期间先将SECURE_COOKIE设为false，运行 `docker compose up -d --build app`。该命令只启动app，4173只绑定服务器127.0.0.1。
3. 在自己电脑建立SSH转发：`ssh -L 4173:127.0.0.1:4173 用户@服务器`。浏览器访问本机127.0.0.1:4173，创建所有者并确认可登录。不要导入真实团队数据前跳过初始化。
4. 将SECURE_COOKIE改回true，确认域名A/AAAA记录已解析到服务器、80/443可访问。执行 `docker compose --profile public up -d --build`，Caddy申请证书并反代app。
5. 关闭SSH转发，使用HTTPS域名重新登录，确认Secure/HttpOnly会话、上传下载、邀请加入和撤权全部正常。安全组不要对外开放4173。

部署变量：DATA_DIR为数据目录；PUBLIC_ORIGIN为可信外网源；SECURE_COOKIE云端必须true；MAX_FILE_BYTES限制上传（默认10MiB）。按实际需要修改这些配置并重启服务。

## 备份与恢复

当前数据库同时保存业务与私有文件字节，备份须包括完整SQLite数据。工程提供SQLite一致备份命令，可在服务运行时生成包含已提交事务和文件版本字节的独立快照：

```powershell
# 在开发目录运行；目标文件必须尚不存在，建议使用日期时间区分。
node server/backup.mjs data/cockpit.sqlite backups/cockpit-2026-10-23.sqlite
```

命令使用 `VACUUM INTO`，完成后执行 `PRAGMA integrity_check`；不会覆盖已存在的目标文件。`DATA_DIR`另设路径时，显式传入对应的 `cockpit.sqlite`，不能把默认data目录当成实际生产数据目录。备份包含账号密码散列、私有文件与业务记录，访问权限应与生产数据库相同；异地副本、加密、保留周期和磁盘配额需在目标服务器配置。

Docker中可在app容器内运行同一命令，快照目标须位于挂载到宿主机的备份目录，随后复制到独立备份目标。若采用维护窗口归档cockpit-data完整卷，也应先停止app；不要在运行中只复制主.sqlite而遗漏WAL。

恢复前先保存现有数据，停服务，将快照复制到**新建独立数据目录**并命名为 `cockpit.sqlite`。不要将快照和旧库的 `cockpit.sqlite-wal`、`cockpit.sqlite-shm` 混放。以独立目录的 `DATA_DIR`启动隔离实例，验证原账号能登录、项目权限正确、历史文件版本下载字节一致，再切换生产卷。备份位置、保留天数和恢复时间目标需要部署时确定；当前不执行自动永久清理。业务导出不等同数据库备份。

可复现演练脚本位于项目根目录 `验证/backup-restore.mjs`。它从源目录取一致快照，在操作系统临时目录建立恢复实例，通过真实HTTP登录并核对原项目、授权及文件版本，最后清理临时恢复目录；不写源库业务。需要源库已有同一资料的v1/v2。运行前仅在当前终端设置 `QA_RESTORE_PASSWORD` 环境变量，然后从项目根执行：

```powershell
node 验证/backup-restore.mjs <已有同一资料v1和v2的隔离测试数据目录> <该测试库所有者邮箱>
```

上面尖括号表示必须替换的参数，不要原样执行；路径包含空格时加引号。原验收使用的 `验证/运行数据-final` 已在阶段清理时移除，需先准备新的隔离夹具。重跑会覆盖 `验证/备份恢复检查.json`，不要为重复测试修改正在验收的设计演示库。密码不要写在命令参数、版本库或报告中。脚本核对源业务前后指纹，若源业务持续变化则要求重试，源库的正常会话/审计变化不作为业务变化。

## 忘记密码与受控运维恢复

当前没有邮箱找回、邮件验证码或隐藏默认口令。成员知道当前密码时可在个人资料修改。工作区**所有者**可在再次输入自己当前密码后，重置其他成员或管理员的密码，服务端同时撤销被重置账号的旧会话。当前实现中管理员不能重置密码，也不能重置所有者；不能把“管理员可管理普通成员”理解为拥有密码重置能力。

第一版只有一名所有者。唯一所有者忘记密码后，平台没有另一个账号可在Web内替其恢复，也不能通过重新打开首次初始化页面另建所有者。账号恢复须由获得明确授权、拥有服务器及数据库运维权限的人在维护窗口处理：

1. 确认恢复请求人与工作区归属，暂停服务及外部写入，先制作并保存一致备份。
2. 在独立恢复库中确认准确的所有者ID与邮箱。按现有实现的scrypt盐值和散列格式生成新的独立密码散列；只更新目标账号，不提升其他账号角色，不把明文密码写进SQL、日志或审计。
3. 撤销目标账号全部会话，并记录不含凭据的运维恢复审计。若有失败登录限流，等待窗口到期或由获授权的运维按实际记录处理。
4. 在隔离实例验证新密码登录、账号角色、项目权限和文件访问，再按停服恢复流程切换；凭据通过已确认的私下渠道交付，首次登录后由本人修改。

仓库目前未提供一键离线改密工具，上述属于受控人工运维流程，不是已自动化或已演练的忘密功能。不能通过删除数据库、修改工作区归属、关闭鉴权或设置通用默认密码完成恢复。
